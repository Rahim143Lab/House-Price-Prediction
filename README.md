# House Price Prediction

An end-to-end, production-style machine learning system that estimates
residential property prices from real-estate features, built as a
portfolio project demonstrating full ML engineering: data pipeline, model
training and comparison, a REST API, and a web dashboard.

> **This is an educational/portfolio prediction system.** It estimates a
> plausible sale price based on historical patterns in one dataset — it is
> **not** an appraisal, and actual property prices depend on many
> real-world factors (market conditions, comparable sales, school
> districts, financing, negotiation, and more) that this system does not
> see.

---

## Overview

Given a set of property details — bedrooms, bathrooms, living area, lot
size, garage capacity, year built, neighborhood, and a handful of other
features — the system returns an estimated sale price, the model used, and
an approximate error band, through both a REST API and a responsive web
dashboard.

## Features

- Clean, reproducible data pipeline (load → clean → engineer → split)
- 6 regression models trained and compared: Linear, Ridge, Lasso, Random
  Forest, Gradient Boosting, XGBoost
- Hyperparameter tuning via `RandomizedSearchCV` on the strongest
  tree-based model
- Proper train / validation / test discipline — the test set is touched
  exactly once
- FastAPI backend with input validation, clear errors, and OpenAPI docs
- Responsive web dashboard with a prediction form, results, model
  performance, and feature importance
- 28 automated tests (pytest) covering preprocessing, the model, and the
  API
- No fabricated numbers anywhere — every metric in this README was
  produced by actually running the pipeline in this repository

## Machine Learning Approach

This is a **supervised regression** problem: predict a continuous target
(`SalePrice`) from a mix of numeric and categorical property features.

1. **Feature engineering** derives features that are meaningful for
   real estate and available at prediction time (see
   [Features](#important-engineered-features) below) — no feature reveals
   the target directly, and no engineered feature depends on information a
   web-form user couldn't provide.
2. **Preprocessing** is a scikit-learn `ColumnTransformer`: numeric columns
   are median-imputed, categorical columns are most-frequent-imputed and
   one-hot encoded with `handle_unknown="ignore"` (so an unseen
   neighborhood value at inference time doesn't crash the API). It is
   fit **only** on training data.
3. **Model comparison** trains 6 regressors, evaluated on a validation set
   never used for fitting.
4. **Hyperparameter tuning** runs `RandomizedSearchCV` (5-fold CV, 20
   iterations) on the strongest tree-based baseline.
5. **Final evaluation** retrains the selected pipeline on train+validation
   and evaluates **once** on the untouched test set — that number is what's
   reported below and returned by the API.

## Dataset

**Ames Housing dataset** (De Cock, 2011) — 2,930 real residential property
sales in Ames, Iowa (2006–2010), with 80+ recorded characteristics. It's a
well-known, freely available regression benchmark and a richer alternative
to the older Boston Housing dataset. See [`data/README.md`](data/README.md)
for source details and how to regenerate the processed splits.

This project uses a curated subset of ~18 features (numeric + categorical)
that mirror what a simple home-value estimator would realistically ask a
user for — not all 82 raw columns.

### Important engineered features

| Feature | What it captures |
|---|---|
| `property_age` | Years between the reference year and `Year Built` |
| `years_since_renovation` | Years since the last remodel/addition |
| `total_bathrooms` | Full baths + 0.5 × half baths, as one number |
| `living_area_per_bedroom` | "Spaciousness" independent of raw square footage |
| `lot_area_per_living_area` | Distinguishes large-lot vs. large-house properties |
| `garage_indicator` / `has_fireplace` / `has_deck_or_porch` | Binary amenity flags |
| `floors` | Approximate floor count, derived from house style |

## Dataset Setup

Nothing to do — `data/raw/AmesHousing.csv` is already included. See
[`data/README.md`](data/README.md) if you ever need to restore it.

## Training

```bash
python -m src.train
```

This loads and splits the data, trains and compares 6 models, tunes the
best tree-based model, retrains on train+validation, evaluates once on the
test set, and saves:

- `models/house_price_model.joblib`
- `models/model_metadata.json`
- `reports/metrics/model_comparison.csv`
- `reports/metrics/best_params.json`
- `reports/metrics/final_test_metrics.json`

## Evaluation

```bash
python -m src.evaluate
```

Generates `reports/figures/actual_vs_predicted.png`,
`residual_distribution.png`, `feature_importance.png`, and
`reports/metrics/feature_importance.csv` from the currently saved model.

To regenerate the EDA figures:

```bash
python -m src.eda
```

## Running the Frontend

The frontend is static HTML/CSS/JS — serve it with any static file server
and make sure the API is running (CORS is open for this portfolio project):

```bash
cd frontend
python -m http.server 8080
```

Then open http://127.0.0.1:8080/index.html. If you host the API somewhere
other than `http://127.0.0.1:8000`, set `window.LEDGER_API_BASE` before
`script.js` loads (e.g. in a small inline `<script>` tag in `index.html`).

## API Documentation

| Method | Endpoint | Description |
|---|---|---|
| GET | `/` | Basic API information |
| GET | `/health` | Health check — `{"status": "healthy"}` |
| GET | `/model-info` | Model name, version, test metrics, supported features, valid neighborhoods |
| GET | `/feature-importance` | Top feature importances from the trained model |
| POST | `/predict` | Predict a house price from property features |

Full interactive documentation (request/response schemas, validation
rules) is auto-generated by FastAPI at `/docs`.

## Model Performance

Validation comparison across all 6 baseline models (from
`reports/metrics/model_comparison.csv`):

| Model | Val MAE | Val RMSE | Val R² |
|---|---|---|---|
| XGBoost | $16,680 | $24,293 | 0.9138 |
| Gradient Boosting | $16,485 | $24,456 | 0.9127 |
| Random Forest | $16,518 | $25,307 | 0.9065 |
| Linear Regression | $18,830 | $28,103 | 0.8847 |
| Ridge Regression | $18,841 | $28,094 | 0.8847 |
| Lasso Regression | $19,124 | $28,363 | 0.8825 |

**Selected model: XGBoost (Tuned)**, chosen because it had the strongest
validation R² among tree-based models and improved further after
`RandomizedSearchCV` tuning (best params: `n_estimators=600`,
`max_depth=3`, `learning_rate=0.05`, `subsample=0.8`,
`colsample_bytree=0.9`).

**Final, one-time test-set evaluation:**

| Metric | Value |
|---|---|
| MAE | $16,385.11 |
| RMSE | $24,861.85 |
| R² | 0.9142 |
| MAPE | 8.93% |

Test performance is close to validation performance (R² 0.914 vs. 0.926),
indicating the model generalizes reasonably well rather than overfitting
to the validation set.

**Top predictive features** (from `reports/metrics/feature_importance.csv`):
`Overall Qual` (quality), `Garage Cars`, `has_fireplace`,
`total_bathrooms`, `Central Air`, `living_area_per_bedroom` —
consistent with real-world real-estate intuition.

## Deployment

**Free options**
- **Render** or **Railway** — deploy `api/main.py` as a web service
  (`uvicorn api.main:app --host 0.0.0.0 --port $PORT`); both have free
  tiers with usage limits.
- **Hugging Face Spaces** — can host the FastAPI backend (Docker SDK) or a
  Gradio/Streamlit wrapper around `src/predict.py`.
- **GitHub Pages** — can serve the static `frontend/` folder (point
  `window.LEDGER_API_BASE` at your deployed API URL).
- **Vercel** — can host the static frontend as well.

**Paid / production options**
- AWS (ECS/Fargate or Lambda + API Gateway), Google Cloud Run, or Azure
  Container Apps for the API, behind a managed load balancer with
  autoscaling and monitoring.

Free-tier availability and pricing on any of these platforms can change —
check current terms before relying on them.

## Future Improvements

- Log-transform the (right-skewed) target for the linear models and
  compare
- SHAP-based explanations per individual prediction, not just global
  feature importance
- A model registry / versioning story (e.g. MLflow) instead of a single
  `.joblib` file
- Authentication and rate limiting if this were to move beyond a
  portfolio project
- A proper confidence interval (e.g. quantile regression or conformal
  prediction) instead of the current ±MAE heuristic band
- CI (GitHub Actions) running `pytest` and linting on every push

## Limitations

- Trained on one regional dataset (Ames, Iowa, 2006–2010 sales) — it will
  not generalize to other cities, price ranges, or time periods without
  retraining on relevant data.
- The "estimated range" shown in the API/UI is a simple ±MAE heuristic,
  **not** a statistical confidence interval.
- No information about school quality, crime, walkability, recent
  comparable sales, or current market trends is used.
- The model can only be as fair or as biased as its training data; it
  should not be used for real financial or lending decisions.
